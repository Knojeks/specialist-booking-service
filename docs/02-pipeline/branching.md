# Стратегия ветвления и правила ревью

## Стратегия ветвления

Выбран **GitHub Flow**: подходит для небольшого веб-сервиса с частыми изменениями. 
Основная ветка — master. Изменения вносятся через отдельные ветки и pull request.

Именование веток: тип/номер-issue-краткое-название. 
Типы: feat — функция, fix — исправление, chore — настройка, docs — документация.

Одна ветка — одна небольшая задача. Плановое время жизни — 1–3 дня с учётом паузы перед самопроверкой. После слияния ветка удаляется.

## Коммиты

Используется **Conventional Commits**: тип: описание. Типы: feat, fix, test, docs, chore, refactor.


## Pull request и правила слияния

- Каждый PR связан с Issue и содержит описание изменений и способ проверки.
- Размер — не более 400 изменённых строк без сгенерированных файлов; большие изменения делятся.
- Самопроверка по чек-листу выполняется через сутки после написания кода. Результаты фиксируются комментарием в PR.
- Слияние допускается после проверки, устранения замечаний и успешного CI. Способ — squash merge, итоговый коммит по Conventional Commits.

## Защита master и шаблоны

Требуется настроить:

- запрет прямых изменений: только через PR;
- обязательный успешный CI, блокирующий слияние при ошибке;
- запрет force push и удаления основной ветки;
- .github/PULL_REQUEST_TEMPLATE.md: цель, связь с Issue, шаги проверки и чек-лист;
- .github/CODEOWNERS: GitHub-аккаунты ответственных за код.
