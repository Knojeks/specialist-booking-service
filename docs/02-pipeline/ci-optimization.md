# Оптимизация конвейера CI

## Цель

Измерить исходное время CI и проверить влияние трёх последовательных оптимизаций.

## Исходные данные

Проект Laravel, GitHub Actions, PR #15.
Исходный конвейер выполняет все этапы последовательно,
без явно настроенного кеширования зависимостей и Docker-слоёв.

Проведено пять успешных запусков одной версии конвейера:
GitHub Actions CI #4, попытки 1–5.
Запуск с намеренной ошибкой в измерения не включён.

## Базовая линия

Время указано в секундах по данным GitHub Actions.
Общее время — длительность задачи CI без ожидания запуска.

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Set up job | 0 | 1 | 1 | 2 | 2 | 1 |
| Download repository | 2 | 1 | 1 | 5 | 4 | 2 |

| Install dependencies | 5 | 8 | 6 | 5 | 5 | 5 |

Значения этапов округлены интерфейсом GitHub.

Общее время взято отдельно из длительности задачи CI.

Расчёт медианы общего времени:
87, 94, 97, 97, 97 → среднее по положению значение — 97 с.

## Критический путь

Все этапы выполняются последовательно в одной задаче CI,
поэтому входят в критический путь.

Самый длительный этап — сборка Docker-образа:
медиана 77 с при общем времени 97 с.
Он является основным кандидатом на ускорение.

## План оптимизации

Изменения применяются по одному с сохранением предыдущих:

1. Кеширование загрузок Composer.
2. Кеширование слоёв Docker.
3. Параллельное выполнение проверок и сборки.

После каждого изменения выполняются 3 успешных запусков.
Их медиана сравнивается с предыдущим вариантом и базовой линией.

## Предварительный вывод

До оптимизации.
Медиана исходного времени CI — 97 с.
Наибольшую часть времени занимает сборка Docker-образа.

## Оптимизация 1 — кеширование Composer

Добавлен actions/cache для сохранения скачанных архивов Composer.
Ключ кеша зависит от composer.lock.

Подготовительный запуск занял 108 с и учитывается отдельно.
Три повторных запуска подтвердили успешное восстановление кеша.

| Показатель | 1 | 2 | 3 | Медиана |
| --- | ---: | ---: | ---: | ---: |
| Вся задача CI | 131 | 94 | 94 | 94 |
| Восстановление кеша | 2 | 2 | 1 | 2 |
| Установка зависимостей | 3 | 2 | 3 | 3 |
| Сборка Docker | 81 | 79 | 78 | 79 |

Медиана общего времени уменьшилась с 97 до 94 с:
(97 − 94) / 97 × 100% ≈ 3,1%.

Установка зависимостей ускорилась, но восстановление кеша
тоже требует времени. Общий эффект небольшой на фоне
разброса длительности запусков. Кеширование сохраняется
для последующих экспериментов.

## Оптимизация 2 — кеширование слоёв Docker

Сборка переведена на Docker Buildx с сохранением и восстановлением
слоёв через кеш GitHub Actions. Кеш Composer сохранён.

Подготовительный запуск занял 137 с и учитывается отдельно.
В повторных запусках использование кеша подтверждено строками CACHED.

| Показатель | 1 | 2 | 3 | Медиана |
| --- | ---: | ---: | ---: | ---: |
| Вся задача CI | 38 | 44 | 36 | 38 |
| Сборка Docker | 14 | 18 | 14 | 14 |

Относительно предыдущего варианта время CI сократилось:
(94 − 38) / 94 × 100% ≈ 59,6%.

Результат получен при готовом кеше и повторной сборке без изменения
кода. При изменении файлов затронутые слои потребуется собрать заново.

## Оптимизация 3: параллельные задачи

Проверки PHP и сборка Docker выполнялись параллельно.
Отдельная итоговая задача CI проверяла успешность обеих задач.

Сравнение по Total duration на странице Summary:

| Вариант | Измерения, с | Медиана, с |
|---|---|---|
| Последовательный, с кешем Composer и Docker | 42, 50, 41 | 42 |
| Параллельный, с теми же кешами | 52, 46, 42 | 46 |

Медиана увеличилась на 4 секунды (9,5%).
На текущем проекте параллельное выполнение ускорения не показало.
Дополнительные затраты на запуск задач и итоговую проверку
могли перекрыть выигрыш.

Критический путь параллельного варианта: Docker build → CI.

По результатам сравнения оставлен последовательный вариант
с кешированием Composer и слоёв Docker.
