# Процесс разработки

## Методология

Выбран **Kanban**.

- Задачи идут непрерывным потоком.
- Следующую задачу берём после завершения текущей.
- Доступно 20 часов в неделю: работа ведётся непрерывным потоком без фиксированных спринтов.
- Зависимости учитываются при выборе следующей задачи, а состояния на доске позволяют измерять время выполнения.

## Доска задач

Используются GitHub Issues и GitHub Projects.

| Колонка | Значение |
| --- | --- |
| Todo | Задача ещё не начата. Перед началом проверяется DoR. |
| In Progress | Выполнение задачи. |
| In Review | Самопроверка по критериям приёмки и DoD. При ошибках — возврат в In Progress. |
| Done | Задача соответствует DoD, Issue закрыта. |

Задачи перемещаются в момент фактической смены состояния.

## WIP-лимиты

- In Progress — не более 1 задачи.
- In Review — не более 1 задачи.
- **Суммарно в In Progress и In Review — не более 1 задачи:** пока текущая задача проверяется, новая не начинается.
- Для Todo и Done лимит не устанавливается. Ограничения соблюдаются вручную.

Обоснование законом Литтла: **L = λ × W**, где L — среднее число незавершённых задач, λ — среднее число завершений за неделю, W — среднее время цикла в неделях.

По закону Литтла при неизменной пропускной способности увеличение среднего количества незавершённых задач увеличивает среднее время их выполнения.

Для одного исполнителя начальный суммарный лимит 1 уменьшает переключения и очереди.

## Definition of Ready

Набор формальных критериев, говорящих о том, что задача готова к взятию ее в работу

1. Понятны цель, границы и принадлежность к MVP.
2. Для истории есть минимум два критерия «Дано / Когда / Тогда» и оценки трудоёмкости и SP.
3. Необходимые зависимости выполнены, данные и доступы подготовлены.
4. Задача достаточно мала, способ проверки понятен, блокирующих вопросов нет.
5. Суммарный WIP-лимит позволяет начать работу.

## Definition of Done

Набор формальных критериев, говорящих о том, что задача выполнена

1. Все критерии приёмки выполнены, ошибки исправлены.
2. Необходимые автотесты добавлены или обновлены и проходят; обязательные проверки CI успешны.
3. Выполнена самопроверка изменений и обработки ошибок.
4. Pull request связан с Issue, изменения объединены в main.
5. Сервис запускается, миграции проверены при их изменении. После введения CD изменение развёрнуто и проверено на учебном стенде; до этого проверяется локальный запуск.
6. Затронутая документация обновлена, способ и результаты проверки записаны в Issue или pull request.

Для задач только с документацией проверяются содержание, расчёты, ссылки и сохранение в репозитории; тесты приложения и развёртывание не требуются.
