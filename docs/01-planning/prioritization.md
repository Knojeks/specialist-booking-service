# Приоритизация историй и выбор состава MVP

## Цель

Рассчитать WSJF, определить предварительную ёмкость одиночного разработчика, сформулировать задачу выбора релиза и сравнить точное и жадное решения.

## Исходные данные

Основа — [видение](vision.md), [бэклог](backlog.md) и [оценки](estimates.md). Используется действующая шкала SP из estimates.md: US-02 = 2 SP, US-01–US-06 суммарно = 25 SP. Время разработчика — 20 часов в неделю. Дата защиты неизвестна.

Оценки ценности и параметры ёмкости ниже — плановые допущения для учебного проекта, а не результаты опроса пациентов или измеренная скорость разработки. После появления даты защиты и фактических данных их нужно пересмотреть.

## Ход выполнения

### Оценка WSJF

Применяется шкала Фибоначчи 1, 2, 3, 5, 8, 13. Большое значение означает больший вклад в соответствующий показатель. Одинаковая шкала применяется ко всем историям.

- Ценность U — насколько функция полезна пациенту или администратору.
- Срочность T — насколько важно получить функцию в первой версии. Здесь нет внешней коммерческой даты: оценивается необходимость для первого работающего сценария.
- Снижение риска R — насколько реализация снижает риск ошибок процесса записи или заранее проверяет существенные технические предположения. Это не сложность истории: размер уже учтён в SP.

V = U + T + R; WSJF = V / SP. V используется как суммарная относительная ценность в задаче о рюкзаке.

### Предварительная ёмкость

Выбран сценарий планирования на 6 недель от начала реализации.

Полезный бюджет: 6 недель × 20 ч/неделю × 0,7 = 84 ч.

Коэффициент фокуса 0,7 учитывает перерывы и незапланированные отвлечения.

Внутри 84 полезных часов предварительно выделены 28 ч на общие работы, не включённые в оценки историй: CI и правила работы с репозиторием — 10 ч; Docker и запуск — 8 ч; развёртывание, общие проверки и подготовка демонстрации — 10 ч.

На истории остаётся: H = 84 − 28 = 56 ч.

Оцениваем, сколько часов приходится на один SP: 79,3333 ч / 38 SP ≈ 2,0877 ч/SP. Для планирования округляем коэффициент вверх до 2,2 ч/SP, вводя небольшой запас.

W = floor(56 / 2,2) = floor(25,45) = 25 SP - сколько единиц SP можно выполнить за эти часы.

Таким образом, бюджет 84 ч распределён между 28 ч общих работ и бюджетом историй. Пересчёт 25 × 2,2 = 55 ч укладывается в 56 ч. 

### Формальная модель рюкзака

Для каждой истории i вводится x_i ∈ {0, 1}: 1 — включить в релиз, 0 — отложить. Вес s_i — её SP, ценность v_i — сумма U + T + R.

Целевая функция:

max Z = 21x_01 + 18x_02 + 19x_03 + 34x_04 + 21x_05 + 21x_06 + 5x_07 + 8x_08 + 8x_09 + 5x_10.

Ограничение ёмкости:

5x_01 + 2x_02 + 3x_03 + 5x_04 + 5x_05 + 5x_06 + 2x_07 + 3x_08 + 3x_09 + 5x_10 ≤ 25.

Зависимости:

- x_03 ≤ x_02 и x_03 ≤ x_06;
- x_04 ≤ x_01 и x_04 ≤ x_03;
- x_05 ≤ x_04;
- x_06 ≤ x_02;
- x_07 ≤ x_02;
- x_08 ≤ x_01;
- x_09 ≤ x_04;
- x_10 ≤ x_01, x_10 ≤ x_03 и x_10 ≤ x_05.

Обязательные истории: x_04 = 1 и x_05 = 1. Запись — основная цель продукта; возможность отмены и уведомление об отмене входят в согласованный пользователем объём. Требование x_04 = 1 математически избыточно при x_05 = 1 и зависимости US-05 от US-04, но сохранено для ясности продуктовых требований.

Транзитивно обязательными становятся US-01, US-02, US-03 и US-06. Регистрация с письмом, вход, расписание и доступ администратора уже находятся внутри этих историй. Веса зависимостей учитываются один раз, даже если одна история требуется нескольким другим.

Результат должен соответствовать объёму 4–6 историй для одного разработчика. Скрипт не поддерживает отдельное ограничение количества историй; в данном наборе оно выполняется автоматически: обязательный набор занимает все 25 SP и содержит 6 историй. Для увеличенной ёмкости это условие нужно проверять заново, а не предполагать, что скрипт его учитывает.

### Решение скриптом

Использован scripts/release_planner.py. Вход — [release-backlog.csv](release-backlog.csv). В CSV value = U + T + R, effort = SP, depends_on — зависимости через точку с запятой, must = 1 для обязательных историй. Дополнительные столбцы U, T и R сохранены для проверки сумм; скрипт их не использует.

Из корня репозитория:

```powershell
python scripts/release_planner.py docs/01-planning/release-backlog.csv --capacity 25
```

### Сравнение методов

Жадный алгоритм сначала включает обязательные истории со всеми зависимостями, затем пытается добавлять остальные по убыванию V/SP вместе с недостающими зависимостями. Он не пересматривает уже сделанный выбор.

Точный алгоритм ветвей и границ ищет наилучший допустимый набор, отсекая заведомо бесперспективные варианты по верхней границе ценности. В этой задаче он посетил 5 узлов поиска.

Расхождений нет: обязательные истории с зависимостями уже занимают всю ёмкость. Поэтому свободного выбора между расширениями не остаётся. 

### Уменьшение ёмкости на 20 процентов

W' = 25 × 0,8 = 20 SP.

```powershell
python scripts/release_planner.py docs/01-planning/release-backlog.csv --capacity 20
```

Скрипт сообщает, что обязательные истории весом 25 SP не помещаются в 20 SP. Вывод сохранён в [release-result-20.txt](release-result-20.txt).

Необходимо пересмотреть срок, доступное время или согласовать уменьшение объёма обязательных историй с повторной оценкой. При прежнем пересчёте не хватает 5 × 2,2 = 11 ч бюджета историй. Молча исключать отмену или регистрацию нельзя: это изменит согласованные границы продукта.

## Вывод

WSJF рассчитан для всех десяти историй с обоснованием трёх компонентов. При предварительном шестинедельном горизонте и явно выделенном бюджете общих работ ёмкость составляет 25 SP. Выбран MVP из US-01–US-06: регистрация и вход, каталог, расписание, запись, отмена и подготовка времени приёма. Письма о регистрации, записи и отмене включены в соответствующие истории.

Точное и жадное решения совпадают: 25 SP, 134 балла ценности, 6 историй. US-07–US-10 отложены. Состав обусловлен обязательными функциями и зависимостями.
